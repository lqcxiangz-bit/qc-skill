# 怎么判断一个 skill 靠不靠谱

skill 是鱼龙混杂的。有的是作者真踩过坑、把事故写成了规矩；有的只是坐在那儿想出来的条条框框。两种长得很像——都是一二三四条、都很有条理、都用加粗——但学第二种是在学噪音。

这份文件讲怎么把它们分开，**而且不靠打分**。

---

## 先说清楚：判断什么、不判断什么

| 不做 | 做 |
|---|---|
| 给它打分（B+、8/10、三星） | 说清**它靠什么假设成立** |
| 「优点三条、缺点三条」 | 说清**你拿不到什么** |
| 通篇按好坏组织，像审稿 | 说清**值不值得你花时间往下读** |

区别在于：分数是个结论，读者只能信或不信；**条件是个句子，读者能拿自己的情况去对**。「它假设你有一台能联网的 Mac，你如果在服务器上跑，它就不管用」——这句话不需要读者相信我，他自己就能判断。

---

## 一、数它的规矩

### 为什么数「不要这样做」最值钱

一份 skill 里份量最重的往往不是「怎么做」，是「**这里会炸**」。

而且看一条禁令带不带理由，能看出它的出身：

```
不要用 SOLID（会渲染成黑色）
                └──────────┘
                 这半句是一次事故被压到最小的样子
```

括号里那半句，是作者真的踩过、真的看见页面变黑、真的改了才写下来的。**它是压缩过的经验。**

反过来：

```
不要用 SOLID
```

光有禁令、没有理由。这可能是真经验没写出来，也可能是拍脑袋定的。**对读者来说没区别——两种情况你都学不到东西，只能照做。**

### 怎么数

```bash
python3 "$SKILL_DIR/scripts/count.py" <目标 SKILL.md>   # $SKILL_DIR 即本 skill 所在目录
```

它会找出所有「不要 / 别 / 不许 / 禁止 / never / don't / avoid」这类句子，分成**说了为什么**和**没说**两堆，顺带数出「犹豫句」和「具体痕迹」（数字、版本号、文件名、报错串）。

**脚本只负责数，不负责下结论。** 正则一定会认错——把「不要」当禁令但其实是「不要紧」，把破折号当理由但其实是插入语。所以：

> **每一条命中都要人工看一眼原文再算数。严禁把脚本吐出来的数字直接当结论贴到页面上。**

不复核就贴，这个 skill 就变回了它明确不做的那件事：拿一个数字冒充判断。

### 三种货色

数完复核完，归到下面三种（可以是混合，如实写比例）：

**一、真踩过坑的**
- 多数禁令带着理由
- 有具体的数字、版本号、文件名、报错串
- 有「犹豫句」——「优先用 A，但遇到 X 换 B」「视情况而定」

> **犹豫是好事，不是缺点。** 作者在这里不给死规矩，通常不是偷懒，是**这个问题本身就没有干净答案**。一份通篇斩钉截铁、一处犹豫都没有的 skill，反而可疑——真做过的人知道哪里没有标准答案。

→ **有东西可学，往下细读。矿在那些括号里。**

> **别只盯着「不要这样做」。** 有的 skill 把经验写在**正面陈述**里——「这样做，因为……」，后面跟着一个具体色号、一次具体的技术故障、一份能核对的清单。
> **带具体证据的正面陈述，和带理由的禁令一样值钱。** 只数禁令，会把这类 skill 误判成「没什么可挖」。

**二、拍脑袋定的**
- 多数禁令光说不要、不说为什么
- 目标写得很模糊——「要专业」「要独特」「要优雅」「高质量」这类**没法验收**的词
- 通篇没有一处犹豫，也没有一个具体数字

→ **照做就行，学不到东西。别做第四问。**

**三、某个工具、某个版本的约定**
- 大多是「这个工具就这么用」「这个版本有这个毛病」
- 换个工具、过一年就不成立

→ **现在管用，但别当知识学。** 页面上要提醒读者：这些是说明书，不是经验。

### 写出来的时候，三条硬规矩

**1. 先说结论，再给证据。不许数字打头。**

数字是你判断的**依据**，不是读者要读的**内容**。读者要的是「所以呢」。

- ✅ **这份 skill 是真踩过坑写的。** 几乎每条「不要这样做」后面都跟着为什么——括号里那半句就是当时出的事。<br>　*依据：23 条「不要」，17 条给了理由。*
- ❌ 脚本数出来：148 句正文里 23 条「不要这样做」，其中 17 条（74%）说清了为什么——所以它算踩过坑的。<br>　（四个数字压在最前面，读者得全扛住才走到意思）

**2. 不许摆出一个你马上要推翻的数字。**

复核之后发现脚本数错了，就**直接用改对的说法**，别把错的数字先摆出来、再解释它为什么不能信。读者不关心你的工具认错了——那是你的事。

- ✅ **它的经验不写在「不要这样做」里，写在正面的规矩里。** 三种 AI 常见长相各给了一个具体色号，一处 CSS 打架给了具体的故障现象。这种是真做过。
- ❌ 脚本数出来 4 条「不要」只有 1 条说了为什么——但这个数字会带偏你，因为……

**3. 别报百分比，别报没有意义的比。**

4 条里的 1 条不是「25%」，是「四条里只有一条」。「33 句正文里 4 条禁令」这种比更是没有意义——分母是什么、多少算多，读者心里根本没有标尺。**能用「几条里的几条」说清，就别换算。**

## 二、写「它靠什么成立」

**只准写成这个句式：**

> 「它假设 ______，你如果 ______，它就不管用。」

三个空都要填满。写不成这句话，说明还没想清楚，**不许放上去**。

✅ 好的：
> 它假设你能在本机跑 Python 脚本，你如果只在网页版对话里用，那两个脚本全都跑不了，剩下的部分要手做。

> 它假设目标 skill 是一份写给人看的 Markdown，你如果拿它去看一份纯 JSON 配置，第四问会全是空话。

❌ 不行的：
> 它比较适合有一定基础的用户使用。（没有假设、没有条件、没有后果——三个空一个没填）

> 它的设计非常巧妙，充分考虑了各种场景。（这是夸奖，不是判断）

**一到三条就够。** 找不出第二条不用硬凑——只有一条真的成立的条件，比三条注水的强。

---

## 三、写「你拿不到什么」

**必须写，不许空着。**

一个只讲好处的介绍，读者没法拿它做决定——因为所有 skill 的介绍都只讲好处，读者早就不看了。写清拿不到什么，反而是这一整页里最让人信得过的部分。

写具体的，不写谦虚话：

✅ 「拿不到：它不会帮你改这个 skill。看完你知道它哪里薄，但改还是得自己动手。」
❌ 「当然它也不是万能的，还有很多可以改进的地方。」

---

## 三点五、先答标题那个问句

「它靠不靠谱」是个问句。**通篇写完，必须有一句话正面答它。**

最容易犯的错是用「值得细读」顶替——那回答的是「要不要往下拆」，是另一个问题。读者读完这一节，脑子里该有的是「**我现在能不能用它**」，不是「我要不要接着往下读」。

三选一，并且把前提摆出来：**能用（前提是…）/ 能用但有前提（…不满足就是空转）/ 不建议用（因为…）**。

**这两件事可以背道而驰**，所以更不能混：
- 一份不靠谱的 skill 可能**很值得拆**——别人怎么翻的车，是最便宜的经验。
- 一份很靠谱的 skill 可能**没什么可拆**——比如它就一句话，好用，但没得学。

---

## 四、怎么说「不值得细读」

**这句话你有权力说，也必须敢说。**

AI 的默认毛病是：给什么都做出一份丰盛产物。一份 4 行的 skill 硬拆成八段长篇细读，那八段全是编的——原文里根本没有那么多判断。

### 一个真实的例子：eli5

Anthropic 官方 plugin 库里有个 skill 叫 eli5，正文全文就这么点：

```
# eli5

Explain like I'm someone who knows nothing about this topic,
using a HTML artifact with big pictures and few words.

Topic: $ARGUMENTS
```

数一下：禁令 0 条，具体痕迹 0 处，犹豫句 0 处。按上面的三种货色，它一条都不占——**它根本没有可挖的判断，因为它把全部力气押在了一条形式约束上**（大图 + 很少的字）。

**正确的做法是：**

第一问照做（它其实特别好画——图就是「一个话题 → 一张图」，中间是空的，那个空本身就是答案）。

第二问如实说：

> 这份 skill 只有 3 句话，没有一条「不要这样做」，也没有一处具体经验。它不是靠规矩多取胜的，是靠一条形式约束——「大图 + 很少的字」——逼出结果。
>
> 值得学的就这一条，已经写在上面了。**没有第四问：再往下拆，拆出来的东西是我编的，不是它写的。**

然后**停在这里**。

### 说「不值得」的时候

- **说清原因**，用数出来的东西说话，不要用形容词
- **不要顺带贬低它**——eli5 很好用，只是没什么可拆的。「不值得细读」说的是**没有可挖的判断**，不是「这东西差」
- **该学的那一点还是要给**，哪怕只有一句

---

## 五、别做这些

- 打分、评级、打星
- 「优点三条、缺点三条」这种谁都会写的对称结构
- 在读者还没搞懂它是干什么的之前，就先说它好不好
- 把 `count.py` 的数字直接当结论
- 因为怕得罪人，明明没什么可拆还硬拆
