# skill-teardown · 批注式长卷拆解

你拿到一个 skill（或文档/作品/提示词）。你的任务不是翻译它，而是**挖出它"为什么这么选"**，并把这份理解做成一篇可读的、用被拆解对象自己的设计哲学生成的 HTML 长卷。

## 一句话原则

最好的拆解不是"复述它说了什么"，而是"还原它为什么这么写"——把每一条规则背后的**思想**和**取舍**挖出来，让读者学会这种思维，而不只是记住规则。

这条原则决定了你的批注不能是泛泛的"这句很重要/很巧妙"。每条批注必须回答一个具体的"为什么"：为什么是小工作室主理人而不是大厂设计总监？为什么不准编号？为什么把独特性的源头放到主题身上而不是设计师灵感上？答得出这种"为什么"的批注才是锋利的。

## 输出：一个 HTML 文件

产出一份单文件 HTML，**用被拆解对象自己的设计哲学来做**——如果拆解的是一个关于设计的 skill，就用它自己教的规则设计这个页面；如果拆解的是别的领域，就用 frontend-design 的通用哲学（见 references/design-philosophy.md）。

### 固定的三段顺序（不要调换）

页面结构严格按这个顺序，因为读者最先想知道的是"这东西值不值得我看"和"它到底怎么跑"，最后才进入逐段细读：

1. **Hero（一篇论点，不是介绍）** —— 用一句断言式标题点出这个 skill 的本质，例如"这不是一个工具，是一段被注入的设计总监人格"。不要写"本文将拆解 XX skill"这种介绍性开头。
2. **研判 / 质量裁决** —— 给一个等级（A / B / C，可用印章式视觉呈现）+ 三段：
   - **好的地方**：它做对了什么，最强的几个设计是什么。
   - **不好的地方**：诚实的局限，依赖什么、不保证什么、对什么场景不适用。
   - **迁移启示**：把这次拆解抽象成一条可迁移的元规则——"写 skill 时优先问……"。
3. **预期使用画面：它到底怎么跑** —— 回答读者最关心的运行问题，放在正文之前：
   - **产出形态**：最后产出的是图、是代码、还是文档？
   - **会不会反问用户**：大多数情况问不问？模糊时问还是自己拍板？
   - **运行轨迹**：用一条横向 5 步左右的流程图把"你发起 → 被动注入 → 内部规划 → 输出成品 → 你看到"画出来，标注每一步"用户可见 / 用户不可见"。
4. **正文长卷（逐段批注）** —— 把原文按语义切成若干段（passage），每段配一个可点击展开的深度批注。

### 正文的双语 / 批注布局规则

这一条很关键，决定页面会不会被撑得过长：

- **原文是非中文**（多数 skill）：每段做成**左英文原文 / 右中文译文**两栏，中间一条竖分隔线；**批注按钮放在两栏下方**，默认折叠，点击才展开。不要把英文、译文、批注三块纵向堆叠，那样页面会非常长。
- **原文是中文**：做成**左中文原文 / 右批注**两栏，批注直接可见或在右侧可展开。

判断"原文是不是中文"看被拆解对象本身的语言，不是看页面语言。

### 批注必须锋利

每段批注的写法，参考 references/insight-patterns.md。核心要求：

- 开头用一个小标签（tag）点明这条批注在回答哪个"为什么"，例如"为什么是'小工作室主理人'而不是'大厂设计总监'"。
- 正文回答**思想层面的取舍**：这个选择关掉了模型的哪条退路？把哪个不可控目标转化成了哪个可控动作？为什么是 A 而不是看似更合理的 B？
- 至少有一处指出"它没说什么"或"它在哪里留了口子"——沉默和例外往往比规则本身更说明问题。
- 可以落一笔到"这个页面自己是怎么执行这条规则的"——让拆解成为示范，而不只是讲解。

如果一条批注删掉后只剩"这句很重要/这条很有洞察"，那它就是不合格的，重写。

## 设计执行（必须遵守）

读 references/design-philosophy.md 和 assets/template.html。template.html 是一份可直接改的骨架，包含暖纸色 token 系统、字体三件套（展示衬线 + 正文衬线 + 等宽）、印章式裁决、横向运行轨迹、左右双栏 + 下方折叠批注的全部结构与 CSS。以它为起点改内容，不要从零搭。

硬性约束：

- **不要暗色系**。用暖纸色 / 浅色背景（纸色 `#f6f2e9` 一类），墨色文字，朱砂/赤陶/苔绿做点缀。这是用户的明确偏好。
- **小字要够大**：正文 ≥ 17px，批注 ≥ 16px，标签/眉标 ≥ 12px。已经很大的标题不要继续加大，只把偏小的字号往上提。批注正文用正文衬线体（不要用别扭的字体），让它读起来像正文而不是脚注。
- **结构即信息**：只在内容真的是序列时才编号（章节用 序/壹/贰/叁 这种中文序数是可以的，因为它们是顺序章节；并列的点不要编号）。
- **把胆量花在一个地方**：选一个 signature 元素（比如批注圆章 + 贯穿脊线），其余保持安静克制。不要到处加渐变和动效。
- **刻意动效**：批注展开用 `max-height` 过渡即可；不要加散落的 fade-in-up / stagger / hover scale 这类无目的动效，它们会强化"AI 感"。
- **显式命名并对抗 AI 默认审美**：暖奶油+衬线+朱砂本身是 AI 的默认长相之一，所以 signature 要押在别的东西上（结构、批注机制、印章），而不是配色渐变。

## 工作流程

1. **读懂原文**：通读被拆解对象，理解它的真实意图，不要停留在字面。
2. **研判**：先在心里给出等级和好坏，写研判段。等级要诚实——A 是真的高质量、值得学习；B 是有亮点但有明显短板；C 是平庸或有害。不要为了好看全给 A。
3. **还原运行画面**：从原文推断它实际怎么跑。如果原文没明说产出形态/是否反问，基于它的形态（纯提示词？带脚本？带工具？）合理推断，并在页面里说明这是推断。
4. **分段 + 写锋利批注**：按语义切 passage，每段写一条回答"为什么"的批注。这是最花时间的部分，也是这个 skill 的核心价值——宁可段数少、批注深，也不要段数多、批注水。
5. **套模板生成 HTML**：基于 assets/template.html 改内容，遵守上面的设计约束。字体用 Google Fonts 引入（Fraunces / Spectral / JetBrains Mono 是一组好搭配，但若被拆解对象本身有强烈字体主张，可换成更贴主题的字族）。
6. **自检**：交付前问自己三个问题——hero 是论点不是介绍吗？批注是回答"为什么"而不是复述吗？页面是浅色且小字够大吗？任何一个否，回去改。

## 什么时候不适用

- 用户只是想要一份纯文字的摘要或翻译，不要可视化页面——直接给文字，别强行做 HTML。
- 被拆解对象本身没有"设计思想"可挖（比如纯函数库的 API 列表）——这种做批注长卷会显得空，先和用户确认是否换形式。
